# 嗒嗒艺术 H5 —— 数据库设计文档

> 数据库：MySQL 8.0
> 字符集：`utf8mb4` / `utf8mb4_general_ci`
> 引擎：InnoDB
> 命名规范：小写下划线；主键 `id`；审计字段统一 `createtime` / `updatetime`（对齐原站 ThinkPHP/FastAdmin 字段风格）
> 时间字段统一 `DATETIME`，金额 `DECIMAL(18,2)`，状态 `TINYINT` + `COMMENT`
> 逻辑删除：`is_deleted TINYINT NOT NULL DEFAULT 0`

## 六、合成与拆分

> ⚠️ 本章表名以**反编译原站 `pages-activity-activity.7618cfa5.js` + 实调 `/api/synthesis/*` 确认的真实路由为准**，
> 原推测的 `compound_*` 命名已废弃（原站前端只拼 `/synthesis/themeinfo`、`/synthesis/material`，无 `compound` 字样）。

**前端状态判定（复刻自原站 `compoundStatus`）**

```
if (stock === 0)          => 已结束
else if (now < real_start)  => 未开始
else if (now > real_end)    => 已结束
else                      => 进行中
```

### 11.3 `collection_list` → 需新增「订单藏品明细」表

详情页区块①「购买明细」的数据源：每个 `collection_list` 元素含

```sql
CREATE TABLE IF NOT EXISTS `order_collection` (
  `id`             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,

  `collection_code` VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '藏品编号，形如 A001/20000',
  `collection_sn`  VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '藏品序列号（缺失时前端显示 --）',
```

### 11.4 `card` → 需新增「E卡」表

```sql
CREATE TABLE IF NOT EXISTS `order_card` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_id`   BIGINT UNSIGNED NOT NULL COMMENT '订单 ID',
  `card_sn`    VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '卡号（前端展示、可复制）',
  `card_keys`  VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '掩码密码，无操作密码时展示',
  `card_pwd`   VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '明文密码，需操作密码校验后才返回',
  `sort`       INT          NOT NULL DEFAULT 0,
  `createtime` BIGINT       NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_order_card_order_id` (`order_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单 E 卡列表（详情页 E 卡区）';
```

安全要点：
1. 详情接口**默认不返回 `card_pwd`**（返回空串），前端因此不渲染密码复制图标
2. 明文密码必须经 `/crystal_goods/getCardCode` 校验**操作密码**（`pay_password`）后单独返回
3. `getCardCode` 需限流（建议 60 秒内 5 次），失败次数达阈值应锁定 E 卡查看
4. `card_pwd` 落库建议加密（AES-128），密钥由环境变量注入，不写入代码库

### 11.5 查询 SQL 参考（订单详情）

```sql
SELECT * FROM `orders` WHERE `id` = :id AND `is_deleted` = 0;

SELECT `collection_code`, `collection_sn`, `from_price`
  FROM `order_collection` WHERE `order_id` = :orderId ORDER BY `sort` ASC, `id` ASC;

SELECT `card_sn`, `card_keys`, '' AS `card_pwd`
  FROM `order_card` WHERE `order_id` = :orderId ORDER BY `sort` ASC, `id` ASC;
```

前端还需 `collection_code` 数组（商品编号 chips / 单值 split('/')），
建议由 `order_collection` 聚合，或在 `orders` 上冗余一个
`collection_codes JSON` 列，详情接口一次性返回。

### 12.3 取消寄售的落库

`changeMarketGoods({ id })` 只接受 `id`，服务端做两道校验：

```sql

SELECT id FROM `consign_records`
 WHERE order_id = :id AND status = 1 AND is_deleted = 0;
-- 无结果 → 返回 code = 0「订单不存在」

-- 2) 乐观更新，仅寄售中可取消
UPDATE `consign_records`
   SET `status` = 3,
       `updatetime` = NOW()
 WHERE `order_id` = :id
   AND `status` = 1;

-- 3) 同步订单主状态为「订单取消」
UPDATE `orders`
   SET `order_status` = 4,
       `updatetime` = NOW()
 WHERE id = :id
   AND order_type = 8
   AND order_status = 1;
```

影响行数为 0 时返回 `code = 0`，前端据此不刷新详情（原站逻辑）。

**约束说明**

| 索引 | 作用 |
| --- | --- |
| `uk_user_collection_code` | **同一用户同一系列内编号唯一**，防止重复铸造；编号全局唯一时也可改为 `UNIQUE (collection_code)` |
| `idx_user_status` | 支撑列表主查询 `WHERE user_id=? AND status=? ORDER BY id DESC` |

### 13.2 字段语义与页面映射

| 字段 | 页面渲染位置 | 取值语义 |
| --- | --- | --- |
| `collection_code` | 卡片 / 弹窗 `#编号`、`MyConsignmentsItem` 的 `#code/total_num` | 该份编号，全局唯一标识 |
| `status` | `getStatus()` 状态文案 | `1` 持有中、`2` 寄售中、`10` 赠送中；`3` 已售出现在「已售」tab（`types=3`） |
| `source_type` | 弹窗来源标签 | 1 购买 / 2 二级市场 / 3 开盲盒 / 4 赠送 / 5 空投 / 6 抽奖 / 7 积分兑换 / 8 合成 |
| `is_lock` | `getStatus()` 第 2 顺位 → 「锁定中」 | 1 时优先于 `status` 判定 |
| `is_link` | `getStatus()` 第 1 顺位的取反条件 | 1 为链接型藏品，不提供「出售」入口 |
| `can_compose` | `getStatus()` 第 4 顺位 → 「可合成」 | 1 时允许发起合成 |
| `day` | 弹窗持有天数 | `now - createtime` 天 |
| `from_price` | 弹窗价格 | 二级市场成交价或寄售底价 |

**`getStatus` 判定优先级**（先匹配先生效，与第十二章寄售状态独立）：

```
1. !is_link && types == 2  → 出售
2. is_lock                → 锁定中
3. status == 2            → 寄售中
4. can_compose            → 可合成
5. status == 1            → 持有中
6. status == 10           → 赠送中
```

### 13.3 「我的藏品」列表聚合查询

原站 `antMycollection` 返回**藏品系列 + 用户持有份数**的聚合结构（一条记录含
`collection` 与 `user_collection` 两个对象），需 join `goods` 与本表并按系列分组：

```sql
SELECT
    c.id                AS collection_id,
    c.name,
    c.listimg,
    c.main_image,
    c.total_num,
    c.batch_id,
    uc.collection_code  AS sample_code,
    uc.total_num        AS series_total_num,
    uc.status           AS sample_status,
    uc.source_type      AS sample_source_type,
    uc.is_lock,
    uc.is_link,
    uc.can_compose,
    uc.day,
    uc.from_price,
    -- 聚合字段
    COUNT(uc.id)                                   AS num,          -- 持有份数 → '持有:N'
    SUM(CASE WHEN uc.is_lock = 1 THEN 1 ELSE 0 END) AS lock_num,     -- 锁仓份数
    SUM(CASE WHEN uc.status  = 3 THEN 1 ELSE 0 END) AS sell_num,     -- 已售份数
    MIN(uc.from_price)                             AS price,        -- 展示价取最低
    MAX(uc.from_price)                             AS total_price   -- 划线原价
FROM user_collection uc
    INNER JOIN goods c ON c.id = uc.collection_id
WHERE uc.user_id = :user_id
  AND uc.is_deleted = 0
  AND uc.status <> 3                              -- types=2 藏品 tab：排除已售
GROUP BY c.id, c.name, c.listimg, c.main_image, c.total_num, c.batch_id
ORDER BY uc.id DESC
LIMIT :offset, :per_page;                          -- per_page = 15（mock 口径）
```

### 13.6 状态流转与 `consign_records` 的关系

`user_collection` 与 `consign_records` 是**一对一活动关系**：一件藏品同一时刻最多挂一条有效寄售。

```
① 发起寄售（pages/consignments/consignments，第 14 页待做）
   INSERT consign_records (user_collection_id, user_id, collection_id,
                              consign_price, status = 1, order_id)
   UPDATE user_collection SET status = 2, updatetime = NOW()
      WHERE id = :user_collection_id AND status = 1 AND is_lock = 0;

② 取消寄售（第 12 页 marketDetail / 第 13 页 MyConsignmentsItem 均调用）
   UPDATE consign_records SET status = 3 WHERE id = :id AND status = 1;
   UPDATE user_collection   SET status = 1 WHERE id = :user_collection_id AND status = 2;

③ 寄售成交（第 14 页待做）
   UPDATE consign_records SET status = 2 WHERE id = :id AND status = 1;
   UPDATE user_collection   SET status = 3 WHERE id = :user_collection_id AND status = 2;
   -- 同时写入买方 user_collection（source_type = 2 二级市场）
   INSERT user_collection (user_id, collection_id, batch_id, collection_code,
                             status, source_type, from_price, createtime)
   SELECT :buyer_id, collection_id, batch_id, collection_code,
          1, 2, :price, UNIX_TIMESTAMP()
     FROM user_collection WHERE id = :user_collection_id;
   UPDATE goods SET sold_num = total_num_sold + 1 WHERE id = :collection_id;
```

**一致性要求**：① ② ③ 三处均为**两步写**，必须包在同一事务内；
② ③ 的 `UPDATE ... WHERE status = 原值` 为乐观锁，影响行数 0 时返回
`code = 0`，前端不刷新列表（原站逻辑）。

### 13.8 索引与性能提示

1. 高频查询是 `user_id + status` 的分页聚合，建议在数据量增长后对

### 14.5 提交寄售的事务

对应 `resale` / `batch_resale`，**单件与多件走同一套事务**，仅流水条数不同。

```sql
START TRANSACTION;

-- ① 校验：所有编号都属于当前用户，且状态为「持有中」且未锁仓
SELECT id, collection_id, collection_code, status, is_lock
FROM user_collection
WHERE id IN (:id1, :id2, ...)     -- user_collection_id.split(',')
  AND user_id = :user_id
  AND is_deleted = 0
FOR UPDATE;

-- 任一行的 status <> 1 或 is_lock = 1 → 整体回滚，返回 code = 0
-- 任一行的 collection_id 与首件不一致 → 拒绝（批量仅支持同系列）

-- ② 校验价格上限
SELECT reprice_limit FROM goods WHERE id = :collection_id;
-- :price > reprice_limit → 返回 code = 0「该藏品寄售价格不得高于 X 元」

-- ③ 生成寄售单（order_type = 8）
INSERT INTO orders
    (order_no, user_id, order_type, order_status, consign_price, divide_id,
     pay_type_name, createtime, updatetime)
VALUES
    (:order_no, :user_id, 8, 1, :price, :divide_id,
     :income_type, UNIX_TIMESTAMP(), UNIX_TIMESTAMP());

SET @order_id = LAST_INSERT_ID();

-- ④ 写寄售流水（每件一条）
INSERT INTO consign_records
    (order_id, order_no, user_id, collection_id, user_collection_id,
     collection_code, consign_price, income_type, status,
     createtime, updatetime)
VALUES
    (@order_id, :order_no, :user_id, :collection_id, :uc_id,
     :collection_code, :price, :income_type, 1,
     UNIX_TIMESTAMP(), UNIX_TIMESTAMP());
-- 多件时循环插入 N 条，status 均为 1（寄售中）

-- ⑤ 更新藏品状态：1 持有中 → 2 寄售中
UPDATE user_collection
SET status = 2, updatetime = UNIX_TIMESTAMP()
WHERE id IN (:id1, :id2, ...)
  AND status = 1 AND is_lock = 0;

-- ⑥ 返回寄售单 id
COMMIT;
-- 返回 { id: @order_id }
```

**校验与失败返回**

| 校验项 | 失败返回 |
| --- | --- |
| 编号不存在 / 不属于当前用户 | `code = 0`「收藏不存在或者已经被删除了」 |
| `status <> 1`（已寄售/已售） | `code = 0`「该藏品已寄售」 |
| `is_lock = 1`（锁仓） | `code = 0`「该藏品处于锁定状态」 |
| 多件跨系列 | `code = 0`「只能寄售同一系列的藏品」 |
| 价格 > `reprice_limit` | `code = 0`「该藏品寄售价格不得高于 X 元」 |
| 操作密码错误 | `code = 1`，`data.password_error = 1` |

**操作密码校验**（在事务之前）：

```sql
SELECT pay_password FROM user_action_pwd
WHERE user_id = :user_id AND status = 1 AND is_deleted = 0;
-- 校验失败 → 返回 { password_error: 1 }，不落库
```

> 密码**必须哈希存储**（`password_hash` + `salt`），校验用 `password_verify`；
> 明文不可落库，也不可写入日志。

### 14.7 状态联动全链路

```
【第十三章】user_collection.status
   1 持有中 ──发起寄售（本页）──→ 2 寄售中
   2 寄售中 ──取消寄售（第12/13页）──→ 1 持有中

   （新建）1 寄售中 ──取消──→ 3 已取消
                   ──成交──→ 2 已售出
```

**取消寄售**（第 12 页详情 / 第 13 页列表共用 `changeMarketGoods`）：

```sql
  AND status = 2;
```

### 15.1 `user_collection` 补充列

第十三章的表结构缺少详情页需要的几个字段，按原站返回补齐：

```sql
ALTER TABLE `user_collection`
```

### 15.3 详情聚合查询

```sql
SELECT
  uc.id                AS collection_id,
  uc.collection_id     AS goods_id,
  uc.collection_code,
  uc.status,
  uc.types,
  uc.cert_time,
  uc.rz_code,
  uc.user_hash,
  uc.user_hash_text,
  uc.is_img_diff,
  uc.diff_name,
  uc.diff_img,
  uc.createtime,
  g.id                 AS product_id,
  g.name               AS product_name,
  g.main_image,
  g.total_num,
  g.is_lock,
  g.weither_regift,
  g.weither_resale,
  g.can_compose,
  g.introduce_image,
  g.purchase_information,
  p.name               AS publisher_name,
  s.name               AS series_name,
  cr.market_goods_id   AS market_goods_id
FROM `user_collection` uc
LEFT JOIN `goods` g              ON g.id  = uc.collection_id
LEFT JOIN `publisher` p          ON p.id  = g.publisher_id
LEFT JOIN `series` s             ON s.id  = g.series_id
LEFT JOIN (
  SELECT cr1.user_collection_id, cr1.market_goods_id
  FROM `consign_records` cr1
  INNER JOIN `market_goods` mg ON mg.id = cr1.market_goods_id
  WHERE mg.status = 1                       -- 1 = 寄售中
) cr ON cr.user_collection_id = uc.id
WHERE uc.id = :id
LIMIT 1;
```

`cr` 子查询按 `market_goods.status = 1` 过滤，保证「取消寄售后 `market_goods.id` 为空」。

### 15.4 盲盒子藏品查询

当 `types = 1`（普通藏品）且该商品配置了子藏品时，返回 `collection_list`：

```sql
SELECT g2.id, g2.name, g2.main_image,
       (SELECT COUNT(1) FROM `user_collection` uc2
         WHERE uc2.collection_id = g2.id AND uc2.is_delete = 0) AS sold_num
FROM `goods` g2
WHERE g2.parent_id = :goods_id
  AND g2.is_delete = 0
ORDER BY g2.sort ASC;
```

> 页面渲染的「共 N 份」用的是**父商品的 `product.total_num`**，不是子藏品数量之和。

### 15.5 取消寄售事务

```sql
START TRANSACTION;

-- 1) 锁定寄售单（FOR UPDATE 防并发）
SELECT id, user_collection_id, status
FROM `market_goods`
WHERE id = :market_goods_id
INTO @mg_id, @mg_uc_id, @mg_status FOR UPDATE;

-- 2) 校验：寄售单存在且仍在寄售中
--    SELECT ... WHERE id = @mg_id AND status = 1
--    不满足 → ROLLBACK，返回 { code:0, msg:'寄售单不存在或已取消' }

-- 3) 寄售单下架
UPDATE `market_goods`
SET status = 3, updatetime = NOW()          -- 3 = 已取消
WHERE id = @mg_id AND status = 1;

-- 4) 写寄售记录终态
UPDATE `consign_records`
SET status = 2, updatetime = NOW()          -- 2 = 已取消
WHERE market_goods_id = @mg_id;

-- 5) 藏品状态回退：寄售中(2) → 已购未寄售(1)
UPDATE `user_collection`
SET status = 1, updatetime = NOW()
WHERE id = @mg_uc_id AND status = 2;

COMMIT;
```

**返回**：`{ code:1, msg:'操作成功', data:null }`，
前端收到后 `emit('refresh')` 重新拉详情，底部按钮由「取消寄售」变回「转赠 + 立即寄售」。

## 十六、转赠（pages/regift/regift 与 pages/regift/record）

> 对应接口：`/user/searchUser`、`/user_collection/user_collection/reGift`、`/user/aboutGift`

### 16.1 涉及表

| 表 | 作用 |
| --- | --- |
| `user` | 转赠发起人 / 接收人（昵称、头像、钱包地址 ntf_url） |
| `user_collection` | 被转赠的藏品（`collection_code` 编号、`status` 状态位） |
| `goods` | 藏品主档（名称、`listimg`、发行量 `total_num`） |
| `user_gift` | **转赠流水**（新增） |

### 16.2 新增表 `user_gift` 转赠流水表

```sql
CREATE TABLE `user_gift` (
  `id`              int(11)      NOT NULL AUTO_INCREMENT,
  `user_id`         int(11)      NOT NULL DEFAULT 0 COMMENT '转赠人 user.id',
  `re_user_id`      int(11)      NOT NULL DEFAULT 0 COMMENT '接收人 user.id',
  `user_collection_id` int(11)   NOT NULL DEFAULT 0 COMMENT '被转赠的 user_collection.id',
  `product_id`      int(11)      NOT NULL DEFAULT 0 COMMENT '冗余 goods.id，便于列表直接取图',
  `price`           decimal(10,2) NOT NULL DEFAULT 0.00 COMMENT '赠送价格',
  `status`          tinyint(1)   NOT NULL DEFAULT 1 COMMENT '1=转赠中 2=已完成 3=已取消',
  `createtime`      int(11)      NOT NULL DEFAULT 0 COMMENT '转赠发起时间（秒）',
  `updatetime`      int(11)      NOT NULL DEFAULT 0,
  `transfertime`    int(11)      NOT NULL DEFAULT 0 COMMENT '完成时间（秒）',
  PRIMARY KEY (`id`),
  KEY `idx_user_gift_user` (`user_id`, `status`),
  KEY `idx_user_gift_re_user` (`re_user_id`, `status`),
  KEY `idx_user_gift_uc` (`user_collection_id`),
  KEY `idx_user_gift_createtime` (`createtime`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='转赠流水表';
```

设计要点：

1. **双向索引**：列表页两个 tab 分别按「我转赠的」（`user_id`）和「我收到的」（`re_user_id`）查询，
   两个索引对称设计，避免 `OR` 条件导致索引失效。
2. **冗余 `product_id`**：列表页每行都要展示藏品图与名称，冗余后可直接 JOIN `goods`，
   无需回表 `user_collection → collection_id → goods`。
3. **`status` 状态位**与 `user_collection.status` 联动：转赠中该藏品不可再操作。

### 16.3 `user_collection` 与转赠的状态联动

`user_collection.status` 已有语义（1=正常 2=寄售中 3=已售出 10=赠送中）。
**转赠提交成功后**，被转赠藏品应置为「赠送中」（10），使第 15 页藏品详情页的
「赠送中（禁用）」按钮态生效；接收方确认接收后置为 1 并在接收方名下生成新记录。

```sql
-- 提交转赠（事务内）
START TRANSACTION;

-- 1) 校验藏品归属与可用状态
SELECT id, user_id, collection_id, collection_code, status
  FROM user_collection
 WHERE id = :user_collection_id
   AND user_id = :user_id
   AND status = 1
   AND is_lock = 0
 FOR UPDATE;
-- 若无行 → 返回「藏品不可转赠」

-- 2) 写转赠流水
INSERT INTO user_gift (user_id, re_user_id, user_collection_id, product_id,
                       price, status, createtime, updatetime)
VALUES (:user_id, :re_user_id, :user_collection_id, :collection_id,
        :price, 1, UNIX_TIMESTAMP(), UNIX_TIMESTAMP());

-- 3) 藏品置为赠送中
UPDATE user_collection
   SET status = 10, updatetime = UNIX_TIMESTAMP()
 WHERE id = :user_collection_id;

COMMIT;
```

接收确认（后续页 `pages/order/regiftDetail` 落地）：

```sql
START TRANSACTION;
UPDATE user_gift
   SET status = 2, transfertime = UNIX_TIMESTAMP(), updatetime = UNIX_TIMESTAMP()
 WHERE id = :id AND re_user_id = :user_id AND status = 1;
-- 校验 affected rows = 1，否则「无权接收该转赠」

-- 生成接收方的新藏品记录（编号沿用，来源标记为转赠）
INSERT INTO user_collection (user_id, collection_id, batch_id, collection_code,
                             token_id, status, is_lock, source_type, createtime, updatetime)
SELECT re_user_id, collection_id, batch_id, collection_code, token_id, 1, 0, 3,
       UNIX_TIMESTAMP(), UNIX_TIMESTAMP()
  FROM user_collection WHERE id = (SELECT user_collection_id FROM user_gift WHERE id = :id);

-- 原藏品置为已转出
UPDATE user_collection SET status = 3, updatetime = UNIX_TIMESTAMP()
 WHERE id = (SELECT user_collection_id FROM user_gift WHERE id = :id);
COMMIT;
```

### 16.4 `aboutGift` 列表查询

`types = 1`（我转赠的）：以 `user_id` 为当前用户；`types = 2`（我收到的）：以 `re_user_id` 为当前用户。

```sql
SELECT
    g.id, g.createtime, g.price, g.status,
    g.re_user_id, g.user_id,
    uc.collection_code, uc.types,
    gd.name, gd.listimg, gd.total_num
FROM user_gift g
LEFT JOIN user_collection uc ON uc.id = g.user_collection_id
LEFT JOIN goods gd            ON gd.id = g.product_id
WHERE g.user_id = :user_id          -- types = 1
  AND g.status <> 3
ORDER BY g.createtime DESC
LIMIT :offset, :per_page;           -- per_page = 15
```

### 16.5 `searchUser` 查询

按 uid / 手机号 / 钱包地址模糊搜索（前端 `w-search-input` 提示「输入用户uid、手机号或钱包地址」）：

```sql
SELECT id, nickname, mobile, avatar, ntf_url
  FROM user
 WHERE (id = :keyword_num AND :keyword_num > 0)
    OR mobile LIKE CONCAT('%', :keyword, '%')
    OR ntf_url LIKE CONCAT('%', :keyword, '%')
 LIMIT 20;
```

**必须排除当前登录用户**（不能自己转赠给自己）：`AND id <> :current_user_id`。
未命中时返回 `code != 1`，前端 toast「用户不存在」。

### 16.6 索引与性能提示

1. `user_gift` 的 `idx_user_gift_user` / `idx_user_gift_re_user` 覆盖两个 tab 的分页查询，
   `ORDER BY createtime DESC` 建议改为 `(user_id, status, createtime)` 复合索引以避免排序。
2. 列表每行都要取 `goods` 的图与名，冗余 `product_id` 已避免多次回表；
   若 `goods` 字段后续频繁变更，建议改为 JSON 快照字段 `product_snapshot`。
3. 提交转赠需对 `user_collection` 行加 `FOR UPDATE`，防止并发重复转赠同一藏品。
4. 手机号脱敏放在**序列化层**完成，不要在 SQL 里 `SELECT` 出明文再由业务代码处理。

## 十七、转赠订单详情（pages/order/regiftDetail）

> 对应接口：`POST /order/order/giveOrderDetail/ids/{id}`、
> `POST /order/order/changeGiveOrderStatus`、`POST /order/pay/doPay`

### 17.1 数据定位

转赠订单是**订单主表 `orders` 中 `order_type = 19` 的一类记录**（由订单列表
`OrderItem.toDetail` 的分发逻辑确认：`19 == order_type → /pages/order/regiftDetail`）。
它与第十六章 `user_gift`（转赠流水）的关系：

| 表 | 职责 |
| --- | --- |
| `user_gift` | 转赠**业务流水**（谁转给谁、哪个藏品、流转状态），驱动第 16/17 页列表 |
| `orders`（`order_type=19`） | 转赠的**资金/结算记录**（支付、取消、退款），驱动第 18 页详情 |

一条 `user_gift` 最多关联一条 `order_type=19` 的订单（转赠免费时可为 0 条；
若转赠需支付手续费/服务费则生成订单，`giveOrderDetail` 即查这张单）。

### 17.2 `orders` 中转赠单的字段约定

沿用第 5.1 节 `orders` 主表，`order_type=19` 时的取值约定：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `order_type` | 19 | 转赠订单（页面据此路由到 regiftDetail） |
| `status` | 1/2/3/5/6/7 | 见 17.3 状态机（**不用** 0/4，与普通订单语义不同） |
| `goods_id` / `goods_type` | 藏品主档 id / 类型 | `goods_type != 1` 时详情页渲染「商品编号」chips |
| `total_amount` | DECIMAL | 详情页「应付金额」；取消/支付弹窗金额取 `total_price`，为空回退 `price` |
| `pay_type` / `pay_status` | 'yibao' 等 | 「收款方式」行（`income_type`：yibao=易宝支付 / huifu=汇付钱包） |
| `service_amount` | DECIMAL | 分账手续费，关联「分账ID号」`buy_order_sn` |
| `pay_time` | BIGINT | 支付时间（秒） |

订单号 `order_no` 前缀实测为 `G`（如 `G20261025000001`），与买入单 `T` 前缀区分，
便于运营侧按前缀检索转赠业务线。

### 17.3 状态机（`ORDER_STATUS_MAP[19]`）

| order_status | 标题 | OrderStatus 文案 | 倒计时 | 底部操作条 |
| --- | --- | --- | --- | --- |
| 1 | 待付款 | 待支付 / 支付倒计时 | `surplus_time_text` 秒（`mm:ss`，`order_type=19` 在倒计时白名单内） | 取消订单 + 确认支付 |
| 2 | 藏品转入成功 | 转入成功 / 可前往我的藏品中查看 | — | 我的收藏 + 继续购买 |
| 3 | 订单已取消 | 已取消 / `updatetime` | — | 继续购买 |
| 5 | 待退款 | 待退款 / `updatetime` | — | **无**（`[5,6]` 分支） |
| 6 | 已退款 | 已退款 / `updatetime` | — | **无** |
| 7 | 藏品转入中 | 转入中 / 正在转入 | — | 转入中（disabled） |

状态迁移：

```
1 --pay/doPay 成功--> 7 --转入完成--> 2
1 --changeGiveOrderStatus(status=3)--> 3
2 --退款流程--> 5 --> 6
```

### 17.4 `giveOrderDetail` 详情聚合查询

详情页四区块（购买明细 / 购买数量+应付金额 / 商品编号 chips / 订单信息）一次聚合：

```sql
SELECT o.id, o.order_no AS order_sn, o.order_type, o.status AS order_status,
       o.goods_id, o.goods_type, o.total_amount AS total_price, o.price,
       o.pay_type, o.pay_way, o.income_type, o.buy_order_sn,
       o.surplus_time_text, o.pay_time, o.createtime, o.updatetime,
       g.name AS goods_name, g.listimg AS goods_cover_image,
       uc.collection_code, uc.collection_sn, uc.from_price
  FROM orders o
  LEFT JOIN goods g ON g.id = o.goods_id
  LEFT JOIN order_goods og ON og.order_id = o.id
  LEFT JOIN user_collection uc ON uc.id = og.user_collection_id
 WHERE o.id = :id AND o.order_type = 19 AND o.is_deleted = 0;
```

要点：

1. **`order_type = 19` 必须进 WHERE**：`orderDetail/ids/{id}` 与 `giveOrderDetail/ids/{id}`
   路径不同但语义相同（都是按 id 查单），后端用 order_type 隔离业务线；
   查不到返回 `{code:0, msg:"找不到该订单或已被删除"}`（原站实测）。
2. **`collection_list`**：购买明细表，一行一个藏品编号（`collection_code` / `collection_sn` /
   `from_price`），由 `order_goods` × `user_collection` 聚合，避免 N+1。
3. **`surplus_time_text`**：支付倒计时剩余秒数，由 `createtime + 支付时限 - now()` 计算；
   仅 `order_status=1` 且 `order_type ∈ (1,2,10,19)` 时下发，前端 u-count-down 消费。
4. **`card`（E卡卡密）**：走独立接口 `/crystal_goods/getCardCode`（需操作密码），
   不并入本查询，防止明文卡密随详情接口泄露。

### 17.5 `changeGiveOrderStatus` 取消事务

```sql
START TRANSACTION;
  SELECT * FROM orders WHERE id = :id AND order_type = 19 FOR UPDATE;
  UPDATE orders SET status = 3, updatetime = :now WHERE id = :id AND status = 1;
  -- 若已锁定藏品（user_gift.status = 1 转赠中），同步释放
  UPDATE user_gift SET status = 3, transfertime = :now
   WHERE user_collection_id = :user_collection_id AND status = 1;
COMMIT;
```

要点：

1. **行锁 + 状态前置条件**（`AND status = 1`）保证幂等：重复点击取消第二次影响行数为 0。
2. 取消后 `user_collection` 若被置为「赠送中」(10)，需回退为正常 (1)，
   使第 15 页藏品详情的「转赠」按钮恢复可用。
3. 原站限制「同一账号一段时间内取消 3 次订单将限购一段时间」——
   建议在 `user` 增加 `cancel_count` / `cancel_limit_time` 两字段，取消时计数，
   达到阈值后在 `orderList` / 下单接口统一拦截（前端 w-toast 已复刻提示文案）。

### 17.6 `doPay` 支付回调

`POST /order/pay/doPay`（`pay_scene:"H5"`）成功后：

```sql
UPDATE orders SET status = 7, pay_status = 1, pay_time = :now WHERE id = :id AND status = 1;
-- 余额支付（balancePay）直接成功；第三方支付以异步通知为准，需做幂等（pay_no 去重）
```

原站 PaySdk 的 `returnurl` 硬编码为 `/pages/order/defaultDetail?id={order_id}`
（转赠单同样返回该地址），复刻时保持原行为；本项目未接入支付渠道，为桩实现。

### 17.7 索引与性能提示

1. `orders` 需补 `KEY idx_orders_type_id (order_type, id)`：`giveOrderDetail` 恒带
   `order_type = 19`，复合索引避免全表扫描；`orderList` 的各 tab 同样按 order_type 过滤。
2. 详情聚合查询的 `ORDER BY` 不存在（按 id 点查），重点是 `order_goods` 的
   `idx_order_goods_order_id` 必须命中，否则购买明细退化 N+1。
3. 取消/支付均为「点查 + 行锁 + 条件更新」，注意 `innodb_lock_wait_timeout`
   与前端 1500ms 自动返回的竞态：后端应快速失败返回 `code != 1`，不要长时间持锁。
4. `user_gift` 与 `orders(order_type=19)` 是 1:0..1 关系，建议在 `user_gift`
   增加 `order_id` 冗余列（第 16.2 节表结构基础上补），便于从转赠流水反查结算单。

### 18.3 `marketList` 查询（`POST /market/market/getMarketList`）

`getCollectionList` 调用，请求体即页面 `form`（`add_deal_num` 恒 true）：

```sql
SELECT g.*, p.name AS product_name, p.listimg
  FROM market_goods g
  LEFT JOIN goods p ON p.id = g.product_id
 WHERE g.status = 1                        -- 在售
   AND (:series_id <> ''  → g.series_id = :series_id)
   AND (:market_type = 3 → g.series_id = -2)      -- 权益资产
   [AND (:keywords <> ''  → p.name LIKE :keywords)]
 ORDER BY
   CASE WHEN :order = 'min_price' THEN g.price END ASC/DESC,
   CASE WHEN :order = 'sale_num'  THEN g.volume END DESC
 LIMIT :page, :list_rows
```

要点：

1. `market_type` 不直接作为过滤列，只映射 `series_id`（1→`""`、2→`3`、3→`-2`）；

2. 排序为「地板价 / 成交量」二选一，`order`/`sort` 成对出现，无排序时按 `sort` 升序。
3. 响应 `data` 为数组（非分页信封），前端直接覆盖 `list`，`loading` 三态驱动 w-loading。

### 18.4 `marketList`（盲盒）查询（`POST /market/market/marketList`）

```sql
 WHERE g.status = 1 AND g.series_id = 3      -- 盲盒大区
 ORDER BY g.sort ASC, g.id DESC
 LIMIT :page, :list_rows
```

要点：

1. 与 18.3 共用 `market_goods`，仅 `series_id` 固定为盲盒大区。
2. 前端 **按页追加**（`page++` 后再次请求并 `$set` 追加），`loading != "loading"` 去重；

3. 响应带 `total/per_page/current_page/last_page`，前端只用 `total` 与 `data`。

### 18.5 系列查询（`POST /index/series`）

```sql

  FROM series
 WHERE type = 10            -- 市场系列
 ORDER BY sort ASC
 LIMIT :page, :list_rows
```

要点：

1. 响应同时驱动三处 UI：大区卡（`current_price`/`change_price`）、分类 tab、
   `is_def=1` 的默认选中（`initDefaultSeries`）。
2. 涨跌幅公式（前端计算）：`change_price ? (current_price-change_price)/change_price : 0`，
   `change_price=0` 时显示 `0.00`（原站含 `change_price ? "0%" : ...` 的反直觉写法，已逐字保留）。
3. 结果进 Vuex `goods.collectionSeries`，市场页 `onLoad` 后不再重复请求。

### 18.6 索引与性能提示

1. `market_goods` 必须有 `KEY idx_mg_status_series (status, series_id)`：市场页所有
   列表查询都带 `status=1 + series_id` 等值条件，该复合索引是表驱动路径。
2. 排序字段 `sort` 建普通索引；`price`/`volume` 的排序走文件排序（数据量小），
   如挂单量过万再考虑 `(status, series_id, price)` 覆盖索引。
3. `LIKE '%kw%'` 搜索无法走索引，关键词检索建议后续接 `goods` 的全文索引或
   ES，市场页当前为前端 mock 过滤。
4. `market_goods.product_id` 与 `goods.id` 的 JOIN 需保证 `goods.PRIMARY` 命中，
   避免嵌套循环回表；`product_name`/`listimg` 已在 `market_goods` 冗余的
   场景下可不 JOIN（见第 5.5 节设计）。

### 19.2 新增表 `buy_beg_order`（求购单）

求购 = 「我要以不低于某价买入 N 份藏品」，是市场的买单方向。求购单创建后，
其他用户可在「以求购价出售」页一键卖出。

```sql
CREATE TABLE `buy_beg_order`
(
    `id`             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
    `order_id`       BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '关联 orders.id',
    `order_no`       VARCHAR(64)     NOT NULL DEFAULT '' COMMENT '订单号，业务唯一',
    `user_id`        BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '求购人',
    `collection_id`  INT UNSIGNED    NOT NULL DEFAULT 0 COMMENT '藏品系列ID',
    `price`          DECIMAL(10, 2)  NOT NULL DEFAULT 0.00 COMMENT '求购单价',
    `number`         INT UNSIGNED    NOT NULL DEFAULT 0 COMMENT '求购份数',
    `filled_number`  INT UNSIGNED    NOT NULL DEFAULT 0 COMMENT '已成交份数',
    `pay_way`        VARCHAR(20)     NOT NULL DEFAULT 'yibao' COMMENT '支付方式',
    `status`         TINYINT         NOT NULL DEFAULT 1 COMMENT '1求购中 2部分成交 3已完成 4已取消',
    `pay_password`   VARCHAR(128)    NOT NULL DEFAULT '' COMMENT '支付密码（加密存储，禁止明文落库）',
    `expire_time`    INT             NOT NULL DEFAULT 0 COMMENT '求购单过期时间戳',
    `createtime`     INT             NULL COMMENT '创建时间',
    `updatetime`     INT             NULL COMMENT '更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_buy_beg_order_no` (`order_no`),
    KEY `idx_bbo_user_status` (`user_id`, `status`),
    KEY `idx_bbo_collection` (`collection_id`, `status`),
    KEY `idx_bbo_expire` (`expire_time`)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4 COMMENT = '求购订单表';
```

字段与接口的映射：

| 页面元素 | 字段 | 来源接口 |
| --- | --- | --- |
| 「不得低于 X 元」 | `floor_price.minprice` | `collectionDetail`（实时地板价，非求购单字段） |
| 提交校验比例 | `floor_price.price_price_ratio` | `collectionDetail` |
| 求购单价 | `price` | `createBegBuyOrder` 入参 → 落库 |
| 求购份数 | `number` / `filled_number` | `createBegBuyOrder` 入参 → 落库 |
| 支付方式 | `pay_way` | `createBegBuyOrder` 入参 → 落库 |
| 「以 X 元买入 N 份」文案 | `price` × `number` | 列表页渲染 |

> **`price` 与 `minprice` 的区别**：`minprice` 是藏品当前地板价（实时行情），
> 求购单的 `price` 是用户承诺的出价。前端校验 `price < minprice` 时阻断提交，
> 服务端同样必须二次校验，防止绕过前端直接调接口挂出低于地板价的求购单。

### 19.3 `createBegBuyOrder` 的落库（一个事务）

```sql
START TRANSACTION;

-- 1) 幂等校验：同一用户对同一藏品不允许存在同价进行中的重复求购单
SELECT id FROM `buy_beg_order`
 WHERE `user_id` = :user_id
   AND `collection_id` = :collection_id
   AND `price` = :price
   AND `status` IN (1, 2)
 LIMIT 1;
-- 有结果 → 直接返回既有订单（幂等），不重复下单

-- 2) 服务端二次校验地板价
SELECT MIN(price) AS minprice FROM `market_goods`
 WHERE `status` = 1 AND `product_id` = :collection_id;
-- :price < minprice → 回滚并返回「当前求购价不得低于地板价的 X%」

-- 3) 写 orders 主表（order_type = 20 求购单）
INSERT INTO `orders`
  (`order_no`, `user_id`, `goods_id`, `goods_type`, `order_type`,
   `status`, `pay_type`, `total_amount`, `pay_status`, `createtime`)
VALUES
  (:order_no, :user_id, :collection_id, :goods_type, 20,
   0, :pay_way, :total_amount, 0, UNIX_TIMESTAMP());

-- 4) 写求购单
INSERT INTO `buy_beg_order`
  (`order_id`, `order_no`, `user_id`, `collection_id`, `price`, `number`,
   `filled_number`, `pay_way`, `status`, `expire_time`, `createtime`)
VALUES
  (:order_id, :order_no, :user_id, :collection_id, :price, :number,
   0, :pay_way, 1, :expire_time, UNIX_TIMESTAMP());

COMMIT;
```

要点：

1. `total_amount = price × number`，`order_type = 20` 与第十二章的寄售 `8` 区分开。
2. `pay_password` 存哈希（如 `bcrypt`），**禁止明文**；`sell` 接口按哈希比对。
3. `expire_time` 默认 `now + 24h`，求购单到期由后台任务置 `status = 4`。
4. 幂等键为 `(user_id, collection_id, price, status IN (1,2))`，避免用户连点造成重复单。

### 19.4 `sell`（以求购价出售）的事务设计

`sell` 是本链路唯一的资金 + 持仓双写操作，必须在**一个事务**内完成：

```sql
START TRANSACTION;

-- 1) 校验支付密码（哈希比对），失败 → 不进入后续步骤
SELECT `id` FROM `buy_beg_order`
 WHERE `user_id` = :seller_id
   AND `status` IN (1, 2)
   AND `collection_id` = :collection_id
 FOR UPDATE;                      -- 行锁，防止并发超卖
-- 无结果 → 返回 code = 0「未找到可匹配的求购单」

-- 2) 校验卖方持仓且未锁仓
SELECT `id`, `collection_code`, `status`, `is_lock`
  FROM `user_collection`
 WHERE `id` IN (:user_collection_ids)
   AND `user_id` = :seller_id
   AND `collection_id` = :collection_id
   AND `status` = 1                -- 1 持有中
   AND `is_lock` = 0;              -- 未锁仓
 FOR UPDATE;
-- 行数 < sell_data 条数 → 回滚，返回「持仓不足或已锁仓」

-- 3) 卖方持仓转为已售出
UPDATE `user_collection`
   SET `status` = 3,               -- 3 已售出
       `sell_num` = `sell_num` + 1,
       `updatetime` = UNIX_TIMESTAMP()
 WHERE `id` IN (:user_collection_ids)
   AND `user_id` = :seller_id
   AND `status` = 1 AND `is_lock` = 0;

-- 4) 求购单成交进度累加
UPDATE `buy_beg_order`
   SET `filled_number` = `filled_number` + :n,
       `status` = CASE WHEN `filled_number` + :n >= `number` THEN 3 ELSE 2 END,
       `updatetime` = UNIX_TIMESTAMP()
 WHERE `id` = :buy_id;

-- 5) 写成交记录（第十二章 consign_records，状态 2 = 已售出）
INSERT INTO `consign_records`
  (`order_id`, `order_no`, `user_id`, `collection_id`, `consign_price`,
   `status`, `buyer_id`, `sold_price`, `divide_id`, `createtime`)
VALUES
  (:order_id, :order_no, :seller_id, :collection_id, :price,
   2, :buyer_id, :price, :divide_id, UNIX_TIMESTAMP());

-- 6) 生成卖方应收（扣除平台服务费）
--    platform_service_price = total_price × platform_service_rate
--    estimated_income = total_price - platform_service_price
INSERT INTO `market_trade`
  (`goods_id`, `price`, `quantity`, `seller_id`, `buyer_id`, `order_id`, `trade_time`)
VALUES
  (:collection_id, :price, :n, :seller_id, :buyer_id, :order_id, UNIX_TIMESTAMP());

COMMIT;
```

**`sell_data` 的解码约定（重要）**

前端提交的是 `btoa(JSON.stringify([{ buy_id, user_collection_id }]))`，
服务端必须先 base64 解码再 JSON 解析，**不能**直接当 JSON 解析：

```php
// PHP
$list = json_decode(base64_decode($sellData), true);
if (!is_array($list)) { return $this->fail('参数错误'); }
```

| 字段 | 含义 | 校验 |
| --- | --- | --- |
| `buy_id` | 匹配到的求购单 ID | 必须属于当前用户的进行中求购单 |
| `user_collection_id` | 卖方要卖出的持仓 ID | 必须属于当前用户、`status=1`、`is_lock=0` |

关键点：

1. **行锁顺序**：先锁 `buy_beg_order` 再锁 `user_collection`，全链路统一顺序，避免死锁。
2. **并发超卖**：`buy_beg_order.number` 是总量上限，`filled_number + n <= number`
   在事务内判定；超出则回滚并提示「求购份数不足」。
3. **服务费**：以 `total_price × platform_service_rate` 计算（0.05 → 5%，
   前端按百分比展示，后端存小数），`estimated_income = total_price - platform_service_price`。
4. 事务提交后再发通知/发币等副作用，**禁止**在事务内做外部调用。

### 19.5 `getSellCollectionInfo` 的组装（可售求购单 × 持仓）

```sql
-- 1) 当前用户对该藏品的进行中求购单（按价格升序，吃单优先）
SELECT `id` AS buy_id, `price`, `pay_way`, `number`, `filled_number`
  FROM `buy_beg_order`
 WHERE `user_id` = :user_id
   AND `collection_id` = :collection_id

 LIMIT :page, :list_rows;
--   → 响应的 selected[]

-- 2) 卖方可售持仓
SELECT uc.id, uc.collection_code, uc.user_hash_text,
       g.name, g.listimg
  FROM `user_collection` uc
  JOIN `goods` g ON g.id = uc.collection_id
 WHERE uc.user_id = :user_id
   AND uc.collection_id = :collection_id
   AND uc.status = 1
   AND uc.is_lock = 0
 LIMIT :page, :list_rows;
--   → 响应的 user_collection_list[]
```

响应字段口径：

| 响应字段 | 计算方式 |
| --- | --- |
| `selected[].price` | 求购单价，前端展示「以 X 元买入 N 份」 |
| `selected[].user_collection_id` | 原站为 `null`（选单阶段未绑定持仓），提交时才绑定 |
| `selected[].collection_code` | 原站为 `null`，提交后由服务端回填 |
| `total_price` | `selected[].price × number`（前端按 `number` 参数计算） |
| `platform_service_rate` | 小数（如 `0.05`），前端按百分比展示 |
| `platform_service_price` | `total_price × platform_service_rate` |
| `estimated_income` | `total_price - platform_service_price` |

> `user_hash_text` 是**脱敏后的持有人标识**（如 `nRqwfK****`），用于「这是谁的藏品」展示，
> 服务端不得返回完整标识。

### 19.7 `myConsignment`（我的寄售）查询

```sql
SELECT o.id, o.order_no, o.order_type, o.order_status,
       o.consign_price, o.goods_name, o.goods_cover_image, o.goods_type,
       o.createtime, o.updatetime,
       uc.collection_code, uc.total_num,
       cr.status AS consign_status, cr.sold_price
  FROM `orders` o
  LEFT JOIN `consign_records` cr ON cr.order_id = o.id
  LEFT JOIN `user_collection` uc
         ON uc.id = cr.user_collection_id
 WHERE o.user_id = :user_id
   AND o.order_type IN (8, 21)          -- 8 普通寄售 / 21 求购成交
   AND o.is_deleted = 0
   AND (:status  = '' OR cr.status = :status)      -- '' 全部 / 1 寄售中 / 2 已成交
   AND (:goods_type = 0 OR o.goods_type = :goods_type)  -- 2 藏品 / 1 盲盒
 ORDER BY o.id DESC
 LIMIT :offset, :limit;
```

要点：

1. 分页信封 `{total, per_page, current_page, last_page, data}`，
   前端 `page < last_page` 才继续 `page++`，否则置「没有更多」。
2. `status` / `goods_type` 为空串或 0 时**不参与过滤**（注意 `''` 与 `0` 的真假判断差异：
   `'0'` 在 PHP 中为假，需用 `=== ''` 严格判断）。
3. `collection_code` 与 `total_num` 来自 `user_collection`，拼成 `#A001/20000` 的
   编号 chips（第 13 章已定义 `user_collection.collection_code` / `total_num`）。
4. 空结果 → 前端 `loadingType = 'empty'`，渲染空态图（原站图 121×122）。
5. `goods_type` 一级 tab 与 `status` 二级 tab 是**正交**的两个维度：
   藏品/盲盒 × 全部/寄售中/已成交，共 6 个 tab。

### 19.8 `user/ranking` 市值排行榜聚合

榜单条目按「用户」维度聚合三个量：**流通量 `flux`**、**最低价 `minprice`**、
**市值 `market_value`**。

```sql
SELECT
    u.id,
    u.nickname AS name,
    u.avatar   AS listimg,
    -- 流通量：该用户持有的有效藏品份数
    COUNT(uc.id)                                   AS flux,
    -- 最低价：该用户持有藏品中的当前最低地板价
    MIN(floor.minprice)                            AS minprice,
    -- 市值 = 流通量 × 最低价
    COUNT(uc.id) * MIN(floor.minprice)              AS market_value
FROM `user` u
JOIN `user_collection` uc
  ON uc.user_id = u.id
 AND uc.status = 1          -- 仅统计持有中（寄售中/已售出不计入流通）
JOIN (
    SELECT `product_id`, MIN(`price`) AS minprice
      FROM `market_goods`
     WHERE `status` = 1
     GROUP BY `product_id`
) floor ON floor.product_id = uc.collection_id
WHERE uc.is_lock = 0
GROUP BY u.id, u.nickname, u.avatar
ORDER BY `market_value` DESC
LIMIT :page, :list_rows;
```

要点：

1. **`market_value = flux × minprice`** —— 榜单并非「历史成交额」，而是
   「当前持仓份数 × 当前地板价」的估算市值，需在文档与 UI 文案中明确，
   否则用户会把「市值」误解为成交金额。
2. 流通量口径：`user_collection.status = 1`（持有中）且 `is_lock = 0`（未锁仓）。
   寄售中（`status = 2`）是否计入需与业务确认；若计入，则 `status IN (1,2)`。
3. `minprice` 取该用户**所有持有藏品地板价中的最小值**（保守估值），
   而非按藏品逐个计算后求和 —— 这与原站卡片「流通:X份 / 最低价:Y / 市值:Z」
   的三段式展示一致（单行只有一个最低价与一个市值）。
4. 响应信封为 `{data: {data: [], my: "", activityRule: ""}}`：
   - `data.data` 榜单数组；
   - `data.my` 当前用户的排名条目（未上榜为空串）；
   - `data.activityRule` 活动规则富文本（对应弹窗正文）。
5. `update_time`（「每日 X 更新」）来自全局配置接口 `/index/config` 一类的缓存，
   非本接口返回；`market_desc`（弹窗规则正文）同源。

### 19.10 索引与性能提示

1. `buy_beg_order` 必须有 `KEY idx_bbo_collection (collection_id, status)`：
   `getSellCollectionInfo` 与 `sell` 的第 1 步都走
   `WHERE collection_id=? AND status IN (1,2)`，该复合索引是表驱动路径。
2. `buy_beg_order` 必须有 `KEY idx_bbo_expire (expire_time)`：
   后台过期任务 `WHERE status IN (1,2) AND expire_time < now` 全表扫代价低。
3. `sell` 的第 2 步依赖 `user_collection` 的
   `idx_user_status (user_id, status, is_lock)`，命中后按主键回表，
   避免对 `user_collection` 做全量扫描。
4. 榜单聚合（第 19.8 节）是**全表聚合 + 子查询 GROUP BY**，数据量增长后
   建议改为**物化汇总表** + 定时任务刷新（每日一次，与 `update_time` 对齐）：

   ```sql
   CREATE TABLE `user_market_value_snapshot` (
     `user_id`     BIGINT UNSIGNED NOT NULL,
     `collection_id` INT UNSIGNED NOT NULL,
     `flux`        INT UNSIGNED    NOT NULL DEFAULT 0,
     `minprice`    DECIMAL(10, 2)  NOT NULL DEFAULT 0.00,
     `market_value` DECIMAL(18, 2) NOT NULL DEFAULT 0.00,
     `snapshot_date` DATE          NOT NULL,
     PRIMARY KEY (`user_id`, `collection_id`, `snapshot_date`),
     KEY `idx_snapshot_date_value (`snapshot_date`, `market_value` DESC)
   ) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '市值榜单日快照';
   ```

   榜单查询改为 `SELECT ... FROM user_market_value_snapshot WHERE snapshot_date = CURDATE()
   ORDER BY market_value DESC LIMIT ...`，把实时聚合降级为日级读，接口 P99 可控。
5. `market_goods` 的 `KEY idx_mg_status_series (status, series_id)`（第 18.6 节）
   同样服务于第 19.8 节的 `MIN(price)` 子查询；该子查询可下沉为
   `market_goods` 上的物化字段 `min_price` + `KEY idx_mg_product_min (product_id, min_price)`。
6. `user/ranking` 的响应体较大（含头像与规则富文本），建议对
   `activityRule` 等富文本做 CDN 缓存或独立配置接口下发，避免每次榜单请求重复下发。
